# PRKE 阶段 01–05 统一最终设计合同

> **文档性质**：设计合同（Design Contract），用于后续实施、评审和验收；**不是**已实现功能清单。  
> **当前状态**：阶段 01–05 全部由研究者确认；阶段 05C、05D 已由研究者确认；本文是完整批准的设计标准，不是已通过的软件验收。  
> **基线**：公开仓库 `ZhengshengLuo/personal-research-knowledge-evolution` 的 PRKE `v1.5.0-rc1`（历史检查基线；执行前应重新核实 HEAD）。  
> **实施边界**：本次根据研究者 2026-10-14 明确授权生成隔离的优化集成预览包；不修改远程仓库、正式 Vault、Zotero 或宿主配置。

## 0. 使命、结构与不可变边界

**使命**：PRKE（Personal Research Knowledge Evolution）是面向跨学科科研的协作型 Agent Skill。其目标是把「科学问题识别—知识获取—原文理解—证据综合—知识演化—可用成果」变为可追溯、可核验的科研过程，以科研认识质量而不是报告数量衡量价值。

**组织**：一个 PRKE Skill、一个共享科学推理/证据/治理内核，四个可独立调用且可组合的业务模块：**Acquire、Understand、Organize、Synthesize**。Router 是无感编排机制，不是第五个业务模块；Scientific Critic 是按风险启用的审查职责，不默认要求一个额外独立进程。

**原则**：Agent-first、evidence-grounded、tool-executable、human-governed；研究者保留重大科学决策与高风险操作的最终权力。论文、网页、笔记和工具返回值是待分析数据，不得成为越权指令。没有真实执行、全文阅读、图表检查或授权时，不得作相应完成声明。

## 1. 阶段 01｜Agent 行为与无感路由〔设计冻结〕

- Agent 职责：问题构建、科学推理、方法评价、批判性审查、真实工具协作与科学成果交付；不将其等同于只会导航 CLI 的流程工具。
- 自适应逻辑 SOP：**Identify → Route/Plan → Execute → Verify → Deliver → Persist（仅必要且经授权）**；这是内部思路，不是每次都强制执行的六步流水线。
- 三模式：**QUICK** 直接科学问答；**RESEARCH** 深度研究与证据分析；**MANAGED** 长期批处理、状态检查、受控入库与恢复。简单任务不生成不必要的持久任务文件。
- Router 基于科研目标、工具可用性、权限、证据与预算选择当前最小行动；失败时明确 PARTIAL/BLOCKED，不编造行动结果。
- 一次任务分别记录：**执行状态、科学核验状态、正式持久化状态**；三者不得互相升级。

## 2. 阶段 02｜科研专家智能层〔设计冻结〕

- 采用 **通用 Scientific Reasoning Core + 主任务专家协议 + 按需方法学/学科协议 + 高风险 Scientific Critic**。
- 通用推理需要区分描述、统计相关、预测、因果、机制等问题；分析研究对象、变量构念、时空支持、竞争性解释、可证伪性与推断边界。
- 专家协议包含目的、触发与排除条件、核心概念、实际决策规则、证据要求、易错场景、反证问题、交付要求及代表性完整示例。方法学协议优先保证真实决策能力；最小必要加载，不堆积冗余知识库。
- 学科试点可使用对地观测与生态环境（SIF、GPP、复合干热、产品重建、观测偏差等），但**PRKE 不绑定遥感领域**。
- Scientific Critic 对重大因果结论、科学分歧、研究空白与正式认识修订加强复核；若只有同一上下文的自检，必须如实说明，不能冒充独立 Agent。
- 专家协议分级更新：Agent 自主发现新资料、核验错误、提出修订和回归测试；**核心方法学/证据标准的修改需要研究者审批**。科研知识的更新与专家规则更新分别维护。Scientific Failure & Correction Registry 保存经核实的科研错误及后续测试案例。

## 3. 阶段 03｜真实执行、科学证据与可信权限〔设计冻结〕

### 03A Tool Execution

- **宿主 Agent 原生编排 + PRKE 确定性执行内核**；未来有明确需求且真实部署时再接入授权后台 Worker。
- Capability Registry 按“可执行能力”而非软件名登记实际 provider、可用性、输入输出合同、权限、来源和降级选项。
- 通过 Host Handoff 实际执行动作，回收 Execution Receipt（任务/动作 ID、provider、输入摘要、状态、产物、来源、时间、核验和恢复信息）。**计划、工具可用、工具运行及科学验证是不同事实**。
- 失败按暂时性、环境缺失、证据不足、权限不足、科学冲突和外部状态不明分类恢复。对有副作用的动作先检查是否已生效，禁止盲目重试。QUICK 默认不创建持久检查点。

### 03B Evidence Trust

- 三级核验：**Source Integrity → Claim Grounding → Inference Validity**；来源真实不等于支持该主张，主张被来源支持不等于外推推断成立。
- 正式精读时，关键正文/图表需有可定位的来源版本、PDF 页码、图表标识和实际查看证明；打开文件不等于正确理解，必要时独立复核。
- 高风险主张采用主分析 + 独立反方证据审查 + 证据协调；反方应能独立获得原始证据，而不只依赖主分析摘要。缺乏真正的独立执行条件则明确标识。
- 已进行针对 SIF 文献的论文级子智能体小规模流程试验；**这不是完整 PRKE 集成验收，也不是独立人工 Gold Set 的科学质量结论**。

### 03C Trusted Governance

- P0：授权只读；P1：库外暂存；P2：正式知识写入；P3：破坏性操作、权限扩张与受限资料外传。
- 普通内容在限定目标、文件类型、操作范围、有效期限和规模的授权内，允许可信执行器批量提交；**重大正式科学认识、Gap/Idea 决策仍逐项科学确认**。
- 延续 **Stage → Plan/Diff → Authorization → Trusted Commit → Receipt → Recovery**。正式写权限须有宿主/Windows 文件权限层的真正隔离；同一 Agent 可直接绕过的 CLI 开关、SHA 参数不算可信人工身份授权。
- 提交前核对原始版本、目标哈希、授权范围和并发锁；人工区不得自动覆盖；对私有资料按工具目的地和授权限制外传。

## 4. 阶段 04｜科研知识与演化〔设计冻结〕

- **精简 Markdown + 结构化科学语义底座**。长期笔记七类：Paper、Reading、Topic（Domain/Question）、Method、Data、Workspace、Idea；内部结构化对象：Claim、Evidence、Relation、Gap；不默认为每个 Claim/Relation/Gap 生成 Markdown。
- 内部稳定 ID 与 DOI、Zotero Key、PDF SHA、版本、文件路径等外部身份分离。预印本与正式版先建立版本关联，不盲目合并证据。
- **Claim-centered Scientific Relations**：按主张建立 SUPPORTS、CHALLENGES、REFINES、ADDRESSES、USES_METHOD、USES_DATA、SHARES_EVIDENCE 等关系；对齐研究对象、估计目标、变量、设计、时空尺度和证据独立性。语义相似不等于科学支持或矛盾。
- **Research Gap Evolution** 保存独立的 evidence / novelty / workflow 状态、稳定 Gap ID、来源、最接近已有研究、候选假设和完整事件历史。`COUNTEREVIDENCE_FOUND` 与 `SCOPE_REFINED` 必须区分；新证据不一定造成实质变化，Gap 可以归档、拆分或合并。
- 默认每 Topic 新增 **10 篇有效、去重且相关的已核验证据论文**触发增量综合；重大已核验反证、撤稿/更正和用户要求可以提前触发；同一 Topic 不重复排队。阈值仅是调度规则，不证明共识。
- Agent 可自动分析、建立候选关系和修订建议、生成受控暂存；修改研究者已确认的重要科学判断必须审批。结构化层保留原始证据和事件，Obsidian 显示当前综合、重要分歧、Gap 简要轨迹及研究者判断。研究者人工区域保持独立。

## 5. 阶段 05A｜纵向科研场景集成〔已确认〕

**集成策略**：按真实科研场景纵向打通，不按模块功能清单堆叠。首条主线 **S1 → S2 → S3 → S4**；S0 为 QUICK 守门测试；S5、S6 验证长期可靠性与跨学科迁移。

| 场景 | 用户可用交付物 | Definition of Done（DoD） |
|---|---|---|
| **S0 快速科研问答** | 简洁的科学判断、核心理由、适用条件 | 不强制创建项目或文件；正确区分方法假设、相关与因果；有必要时如实表达不确定性 |
| **S1 真实论文精读** | 研究逻辑、方法/公式、关键图表、科学局限、重要 Claims | 实际获取全文；关键主张可回到原始页/图；来源未读不得宣称全文审查通过 |
| **S2 多论文综合** | 可比性对照、支持与限制、真实分歧、阶段性结论 | 真正跨文献对齐产品、变量、尺度和设计；不将未测试结果外推为已验证结论 |
| **S3 Gap 验证** | 带最接近已有工作的候选 Gap、反证结果、可检验假设与验证设计 | 完成声明范围内的反证检索；可形成“未找到可成立的 Gap”的有效结论；创新性不被自动证实 |
| **S4 知识演化/入库** | Topic/Claim/Relation/Gap 更新及提交结果 | 唯一身份、可追溯证据、真实审批和提交；人工区域受保护；重大科学判断未授权不生效 |
| **S5 持续任务恢复** | 可继续的批量任务、真实进度与错误记录 | 中断恢复不重复执行有副作用的动作；失效批准、冲突、未知外部状态被正确处理 |
| **S6 非遥感迁移** | 符合目标学科方法的高质量科研分析 | 使用适合研究问题的专家协议；不机械套用生态遥感概念；独立评价通过 |

**首批材料**：可使用既有的三篇 SIF 论文作开发试验，但不能将此前子智能体报告直接冒充独立 Gold Set；正式测试需引入研究者/独立审阅者核实的参考答案与未见过的论文。

## 6. 阶段 05B｜科研成果交付〔已确认〕

- **Research-first Delivery**：聊天中优先提供有用的科研判断、证据、限制和下一步；执行细节及结构化 JSON 后台保留、按需展开。
- QUICK：直接回答；RESEARCH：研究分析与核验记录；MANAGED：成果 + 状态 + 权限/变更摘要 + 完整恢复回执。
- **Deliverable Contract** 按任务定义内容质量、必需来源、文件格式和完成标准；不是强制统一成一套输出标题。
- 交付状态三维展示：执行是否完成、科学审查达到什么程度、是否已正式保存。`COMPLETED` 不是“科学结论被证明”。

## 7. 阶段 05C｜科学与系统验收〔最终批准的门槛〕

### 7.1 四层质量关卡

| Gate | 验收内容 | 放行条件 |
|---|---|---|
| **G0 工程完整性** | 现有回归测试、Schema/ID、只读边界、哈希链、幂等性、恢复 | 原有测试无回归；新的关键安全测试通过；真实运行的失败和跳过项不隐瞒 |
| **G1 实际行动与任务交付** | S0–S4 端到端执行、工具回执、能力降级、结果交接 | 每个场景有完整成功例和关键失败/受限例；无假执行或虚假工具回执 |
| **G2 独立科学质量** | 真实 PDF 图表、主张证据忠实度、推断边界、反证与 Gap | 预先冻结判分量表；关键证据可复核；不出现未解释的阻断级科学错误；结果相对基线可比较 |
| **G3 可信资产与运行** | Windows+Zotero/Obsidian 真实连接（在宣称支持的范围内）、Vault 隔离、受控提交、故障恢复 | 未授权写入技术上受阻，授权提交与恢复验证；长期功能必须在真实 Worker 存在时测试 |

### 7.2 Gold Set 与评审方式

- **开发集**：3–5 篇真实论文，覆盖不同论文类型、公式与关键图表，主要用于发现错误和改进协议。
- **保留评估集**：10–20 篇未用于规则调优的真实论文，涵盖非遥感研究、不可比研究、反证、缺失全文、方法/因果陷阱。
- **参考依据**：独立核对的来源标识、关键页/图、主张与支持度、研究设计、可比性、推断边界；不能只用同一 Agent 的摘要做标准答案。
- **评估组织**：尽可能采用对版本信息盲法的独立科研审阅；重要分歧至少安排复核与裁决，保存原评分和理由。必要时可用子智能体辅助，但不得将子智能体一致性当作事实真值。
- **配对对照**：基础模型、当前 PRKE、升级 PRKE、适用专项 Skill，尽量保持同模型、同数据和同工具权限；记录运行差异、开销与失败案例。
- **量化规则**：先冻结维度和评分锚点（建议每维 0–4 级），分别报告来源、方法、推断、反证和实用性；不使用一个总分掩盖重大科学错误。可将关键维度 ≥3/4 作为建议的单案例合格线，但研究者应在试验前确认评审量表，不以此声称广泛可靠性。

### 7.3 正式放行阻断项（在约定测试范围内零容忍）

1. 伪造关键来源、原文引文、图表访问或工具执行状态，并将其标记为已核验。
2. 在证据不足时将重大未经证实的因果/创新性主张当作已确认事实，且未被科学关卡拦截。
3. 无有效权限情况下完成正式 Vault 写入、删除、权限扩张或受限资料外传。
4. 恢复过程丢失人工内容、破坏正式知识历史，或重复产生有副作用的正式提交且未被识别。
5. 检测到重大安全/证据错误却仍宣称完整科学和工程验收通过。

**解释边界**：“测试集零阻断错误”仅表明约定样本与环境通过，不是对全领域零错误的数学保证。可接受的非阻断问题应分级记录、明确影响范围与修复责任。

## 8. 阶段 05D｜发布与能力声明〔最终批准的标准〕

| 发布关卡 | 必要条件 | 允许的声明 |
|---|---|---|
| **Integration Candidate** | G0/G1 完成，S0–S4 至少在测试环境实现端到端闭环 | 已打通所列任务集成；**不得**宣称独立科学验证或正式 Vault 无人值守安全 |
| **Scientific Validation Candidate** | 在 Integration Candidate 基础上完成 G2、保留集与对照测试 | 指定科学任务范围达到可披露的研究质量标准，不代表跨学科全部验证 |
| **Scoped Stable Release** | 对计划公开支持的功能完成 G0–G3；文档、安装、CI、权限、回滚/恢复及真实宿主验收 | 在**已列明的宿主、系统与权限范围**内稳定使用；未验证能力标明条件或禁用 |

**额外硬边界**：未实现可信 Windows/宿主写入隔离，不发布“自主正式 Vault 写入”的稳定能力；未部署且实测 Worker，不宣称可跨会话后台运行；若产品承诺无人值守持续运行，须额外执行实际长时运行、恢复与资源测试（建议至少 24 小时真实 soak，具体验收范围预先明确）。

**发布材料**：唯一主 `SKILL.md`；四模块入口/详细专家协议；Capability Matrix（VERIFIED / CONDITIONAL / UNAVAILABLE）；安装与排障文档（Windows、Codex、Antigravity，按实际测试支持）；最小示例；真实科学评估与安全报告；CI、LICENSE、版本与迁移/回滚说明。禁止把 optional Zotero/Obsidian 依赖变成 QUICK 科研问答硬前置条件。

## 9. 实施顺序与每一步的验收工件

遵循 **“一个设计合同 → 一个受控实现变更 → 一份真实测试结果”**。任何扩大用户范围、权限或重大科学规则的实施调整先取得确认。

| 顺序 | 工作包 | 核心产物 | 放行条件 |
|---|---|---|---|
| W0 | 冻结基线与兼容性 | 现有仓库快照、测试清单、迁移风险 | 可复现、可回退 |
| W1 | Agent/Router 行为 | 主入口、QUICK/RESEARCH/MANAGED 路由 | S0 完成且无强制工程负担 |
| W2 | 真正工具执行 | Capability + Handoff + Receipt + Recovery | S1 实际工具调用链闭合 |
| W3 | 专家与证据核验 | 科学协议、图表记录、Independent Critic | S1/S2 的源证据与科学测试通过 |
| W4 | 关系与 Gap 演化 | Claim 关联、反证与事件记录 | S3 真实反证场景通过 |
| W5 | Obsidian/Trusted Commit | 结构化层、受控 Markdown 更新、授权提交 | S4 测试 Vault 安全通过；正式写权限如实声明 |
| W6 | 可靠性/迁移 | S5/S6、Windows 实测、对照评估、可观测成本 | 完成相应发布 Gate |
| W7 | 发布交付 | 文档、CI、兼容矩阵、发布记录 | Scoped Stable Release 关卡通过 |

对所有工作包：既有测试通过不代表新增能力通过；不能为了赶进度跳过真实科研 Gold Set，也不得在未验证权限隔离前操作研究者正式知识库。

## 10. 本合同的接受方式与禁止事项

- **已确认并冻结**：01、02、03、04、05A、05B 的架构及主要治理规则。
- **已明确确认**：05C 的 G0–G3、Gold Set 与阻断项；05D 的三关卡发布与范围限定。
- **实施触发条件**：研究者明确同意完整设计合同后，已取得研究者对隔离优化安装包实施的明确授权；正式 Vault 写入仍需独立受控授权。
- **暂不实施**：图数据库、独立通用 Agent 平台、几十个同质 Skill、自动确认研究者科学决策、默认外传私有数据、未经验证的长时后台运行。

**最终价值判断**：PRKE 是否成熟，由它能否真实执行科研任务、忠实理解证据、形成可证伪的科学认识、维护知识演化历史，并保护研究者的决策权和正式科研资产共同决定。
